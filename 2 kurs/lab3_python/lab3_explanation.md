# Лабораторная работа 3 Порождающие шаблоны проектирования

Подробный разбор реализации текстовой RPG на Python и подготовка к защите.

Работа демонстрирует пять способов организации создания объектов: Одиночку, Строителя, Прототип, Фабричный метод и Абстрактную фабрику. Практический результат — консольная игра с героями, снаряжением, торговлей, боями и тремя локациями. Полный код расположен в каталоге labs/lab3; здесь объясняется его устройство и порядок демонстрации.

## 1 Цель и требования работы

Цель — понять, как отделять создание объектов от кода, который их использует. Паттерн задаёт структуру решения повторяющейся задачи проектирования; конкретные классы и методы зависят от приложения.

По заданию необходимо реализовать небольшую текстовую RPG и показать в консоли все пять порождающих паттернов. Для Фабричного метода нужны минимум два подкласса создателя. Для Абстрактной фабрики нужны минимум две конкретные фабрики, каждая создаёт семейство минимум из двух продуктов. Также требуется показать идентичность экземпляров Одиночки, создание через Строителя и независимость копий Прототипа.

В решении использованы три локации и три стартовых набора. Отдельная программа demo.py выполняет обязательную демонстрацию одним запуском.

Факт: все пять паттернов присутствуют в приложенном примере. Поэтому самостоятельное переписывание их реализации не требуется; основной код перенесён из Python документа. Восстановлены склеенные строки, код разложен по отдельным файлам, добавлены файлы __init__.py. Игровые правила и характеристики оставлены как в примере. Проверки и документация добавлены отдельно.

Допущение: выбран Python, поскольку отдельный приложенный документ содержит практику именно на нём. Основной документ разрешает любой язык.

## 3 Сценарий игры

Игрок выбирает воина, следопыта или мага и вводит имя. Строитель получает класс, имя и фабрику стартового набора. Фабрика выдаёт оружие и броню, после чего build проверяет данные и создаёт героя.

В лагере доступны экспедиция, смена снаряжения, торговец и выход. Для начала удобно выбрать воина и мистический лес. Лес рассчитан на начальный уровень, склеп имеет рекомендуемый уровень 3, логово дракона — 5. Рекомендация не является запретом: программа позволяет выбрать более опасную локацию раньше.

Перед экспедицией герой восстанавливает здоровье. Локация создаёт своего врага, запускает бой и начисляет награду либо штраф. За победу начисляются опыт и золото; с некоторой вероятностью появляется предмет, иногда зачарованный. За поражение герой теряет половину золота с округлением вниз. На следующую экспедицию он снова отправляется с восстановленным здоровьем.

Бой автоматический: герой атакует первым, затем выживший враг отвечает. Игрок выбирает локацию и снаряжение, но не выбирает действие в каждом раунде. Цель — победить дракона. После победы игра выводит сообщение и оставляет доступ к лагерю.

Прогресс хранится в памяти. Запись сохранений в файл в этом примере не реализована.

## 5 Базовые абстракции и данные боя

Combatant в combat/combatant.py — абстрактный класс для героя и врагов. Он требует свойства code, name, health, max_health и методы is_alive, roll_damage, receive_hit. Battle использует этот контракт и не проверяет, сражается ли воин с гоблином или маг с драконом.

ABC задаёт абстрактный базовый класс. Декоратор abstractmethod отмечает метод, который обязан реализовать конкретный наследник. Создать экземпляр класса с не реализованными абстрактными методами нельзя. В Python также существуют другие способы описания интерфейсов; в этой работе выбран ABC.

Hit хранит damage и critical. Например, Hit(20, True) означает критический удар с уроном 20. frozen=True запрещает обычное присваивание полям после создания. Это удобно для результата вычисления: удар описывается как значение.

Side различает героя и врага. EventType различает обычный удар, критический удар и смерть. Outcome различает победу и поражение. Enum помогает использовать ограниченный набор именованных значений вместо произвольных строк.

BattleEvent содержит номер раунда, тип события, источник, цель, урон после защиты и здоровье цели после удара. Participant — снимок кода, имени и максимального здоровья участника для отчёта. BattleReport содержит этих участников, исход и кортеж событий. Rewards хранит опыт, изменение золота, добычу и число полученных уровней. ExpeditionReport объединяет seed, код локации, отчёт боя и награды.

Кортеж предотвращает добавление или удаление элементов через этот интерфейс. Однако он не делает вложенные изменяемые объекты неизменяемыми: например, предмет в Rewards.loot остаётся обычным изменяемым Item.

## 6 Одиночка Singleton

Основной файл — core/dice.py. Задача: все случайные решения игры должны обращаться к одному объекту Dice с одним генератором random.Random.

Ключевой фрагмент из реализации:

```python
class Dice:
    _instance: Dice | None = None

    def __new__(cls) -> Dice:
        if cls._instance is None:
            cls._instance = super().__new__(cls)
            cls._instance._random = random.Random()
        return cls._instance
```

_instance — поле класса, общее для обращений к Dice. При первом Dice() значение равно None: создаётся объект и его генератор. При следующих вызовах возвращается сохранённый объект. Создание отложено до первого обращения, поэтому инициализация называется ленивой.

__new__ отвечает за получение экземпляра. __init__ инициализирует уже полученный объект. Инициализацию генератора разместили внутри первой ветки __new__, чтобы очередной Dice() не сбрасывал генератор.

Метод reseed(seed) задаёт начальное состояние генератора; roll(low, high) возвращает целое число в замкнутом диапазоне; chance(p) проверяет событие с вероятностью p; pick(options) выбирает элемент последовательности; next_seed создаёт seed для очередной экспедиции.

Показ на защите:

```python
first = Dice()
second = Dice()
print(first is second)
```

Результат True показывает, что обе переменные ссылаются на один объект. Оператор is проверяет идентичность, а == проверяет равенство по правилам типа.

Преимущества: единый источник случайности и удобный доступ без передачи через каждый конструктор. Недостатки: глобальное изменяемое состояние, скрытые зависимости и влияние запусков друг на друга, если забыть переустановить seed.

Ограничение: реализация рассчитана на обычные вызовы Dice() в однопоточной игре. Она не содержит синхронизации первой инициализации и не является защитой от намеренного обхода средствами языка. В тестах генератор можно переинициализировать и подменять методами тестирования; проблема состоит в сложности изоляции глобального состояния, а не в абсолютной невозможности подмены.

Уточнение к смыслу примера: для воспроизводимости не обязателен именно Singleton. Возможен один явно передаваемый генератор. Здесь Singleton выбран для изучения паттерна.

## 7 Прототип Prototype

Основные файлы — item/item.py и item/item_catalog.py. Каталог хранит настроенные шаблоны предметов. Покупка, стартовый набор и добыча получают копии шаблона.

Ключевой метод:

```python
def copy(self) -> Item:
    clone = copy.copy(self)
    clone._enchantments = list(self._enchantments)
    return clone
```

copy.copy создаёт новый объект того же конкретного класса. Но его поля первоначально ссылаются на те же вложенные объекты. Поэтому изменяемый список зачарований нужно заменить отдельным списком. Иначе добавление зачарования одной копии изменит и другую копию, и шаблон.

Элементы списка — объекты Enchantment с frozen=True и простыми неизменяемыми полями. Их можно безопасно разделять между списками. Новым должен быть сам список, а не обязательно каждое зачарование.

ItemCatalog.register сохраняет прототип по строковому коду. create находит шаблон и вызывает prototype.copy(). Методы create_weapon и create_armor дополнительно проверяют тип результата. Каталог не обязан знать, как создавать каждый класс оружия с нуля.

В default_catalog.py зарегистрированы тренировочный и железный мечи, луки, посохи и разные виды брони. Каждый экземпляр имеет код, имя, базовую цену и характеристики. Sword, Bow и Staff различаются поведением, а разные мечи могут отличаться только данными.

Показ на защите: создать два железных меча, наложить FIERY только на второй и создать третий из каталога. Первый и третий имеют урон 17; второй — 23. Расчёт: 17 + 6 = 23 единицы урона. Цена зачарованного предмета также увеличится на bonus_price.

Преимущества: копирование заранее настроенных объектов без привязки клиента к их конкретным конструкторам. Недостатки: каждое новое изменяемое поле нужно учитывать; при сложных графах ссылок копирование требует отдельного проектирования.

Поверхностная копия создаёт внешнюю оболочку и разделяет вложенные ссылки. Глубокая копия рекурсивно копирует вложенные данные с учётом механизма копирования. В работе выбрана поверхностная копия с отдельным копированием изменяемого списка. Полное deepcopy здесь не требуется.

## 8 Оружие броня и зачарования

Item содержит общие поля, вычисление цены, добавление зачарования и метод копирования. Weapon добавляет базовый урон и абстрактный roll_damage. Armor добавляет долю поглощаемого урона.

Sword возвращает постоянный урон без критического удара. Bow проверяет случай критического удара и при успехе удваивает урон оружия. Staff выбирает целое число в диапазоне вокруг базового урона. Важный порядок: бонус уровня герой добавляет уже после результата оружия, поэтому этот бонус не удваивается критическим ударом лука.

SHARP добавляет 3 единицы урона и 20 золота к цене; FIERY — 6 урона и 50 золота. STURDY добавляет 0,05 к защите и 20 золота; WARDING — 0,10 к защите и 50 золота. Бонус 0,10 означает десять процентных пунктов: защита 30 процентов становится 40 процентов.

Предмет проверяет, подходит ли ему зачарование. Оружие принимает SHARP и FIERY, броня — STURDY и WARDING. Неподходящее зачарование вызывает ValueError. Максимальная доля защиты брони — 0,75, то есть 75 процентов.

## 9 Абстрактная фабрика Abstract Factory

Основной файл — kit/starter_kit_factory.py. Фабрика создаёт семейство связанных продуктов: оружие и броню стартового набора.

```python
class StarterKitFactory(ABC):
    @abstractmethod
    def create_weapon(self) -> Weapon: ...

    @abstractmethod
    def create_armor(self) -> Armor: ...
```

Три конкретные реализации используют общий каталог прототипов:

| Фабрика | Оружие | Броня |
|---|---|---|
| WarriorKitFactory | Тренировочный меч с уроном 12 | Кольчуга с защитой 30 процентов |
| RangerKitFactory | Охотничий лук с уроном 10 и шансом крита 30 процентов | Кожаная броня с защитой 20 процентов |
| MageKitFactory | Посох ученика с уроном от 10 до 18 | Льняная роба с защитой 10 процентов |

HeroClass хранит код, название, базовое здоровье и класс фабрики. starter_kit(catalog) создаёт подходящий объект фабрики. Строитель вызывает два метода этой фабрики и получает согласованный начальный набор.

Семейство определяется игровой ролью: меч и кольчуга относятся к стартовому набору воина. При этом все виды брони представлены одним классом Armor с разными параметрами. Для выполнения требования о двух продуктах достаточно двух разных ролей продуктов — Weapon и Armor.

Преимущества: клиент работает через общий контракт; новый класс героя можно добавить через новую фабрику и регистрацию в HeroClass. Недостаток: добавление нового вида продукта, например зелья, потребует изменить интерфейс фабрики и все реализации.

Абстрактная фабрика согласует стартовую комплектацию. Она не запрещает герою позже экипировать чужое оружие или броню: в игре такой запрет отсутствует. Строитель также позволяет явно задать предметы через set_weapon и set_armor.

## 10 Строитель Builder

Основной файл — hero/hero.py, вложенный класс Hero.Builder. Строитель собирает параметры героя по шагам, проверяет их и передаёт готовые значения конструктору Hero.

```python
hero = (
    Hero.Builder()
    .set_name("Артур")
    .set_hero_class(HeroClass.WARRIOR)
    .set_starter_kit(HeroClass.WARRIOR.starter_kit(catalog))
    .set_level(3)
    .build()
)
```

Каждый set метод изменяет состояние строителя и возвращает self — тот же объект строителя. Благодаря этому следующий метод можно вызвать сразу в цепочке. set_starter_kit получает оружие и броню от абстрактной фабрики.

Метод build проверяет имя, класс, оружие, броню, уровень и золото. Имя должно быть непустым и не длиннее 20 символов; уровень — не меньше 1; золото — неотрицательным. Для уровня по умолчанию используется 1, для золота — 50. Если проверка не пройдена, выбрасывается ValueError, и герой не создаётся.

Hero.__init__ копирует значения из строителя в поля героя и устанавливает текущее здоровье равным максимальному. В Python это соглашение использования: язык не делает конструктор закрытым и позволяет вызвать Hero(builder) напрямую, обходя build.

Преимущества: понятные имена шагов, значения по умолчанию и централизованная проверка целого объекта. Недостатки: дополнительный класс, дублирование полей и необходимость следить за допустимыми комбинациями параметров.

По сравнению с длинным позиционным конструктором цепочка легче читается: set_level(3) не перепутаешь с set_gold(3). Но именованные параметры Python также решают проблему порядка аргументов. В этой работе Builder полезен прежде всего для отдельного шага комплектации и итоговой проверки.

Строитель создаёт отдельный объект Hero, но передаёт ему ссылки на оружие и броню. Повторное использование одного строителя для разных героев может привести к разделению предметов. Основная программа создаёт новый строитель для каждого героя и получает новые копии предметов от фабрики.

## 11 Характеристики и поведение героя

Hero реализует Combatant. Он умеет атаковать, получать урон, восстанавливать здоровье, получать опыт, менять золото, добавлять и удалять предметы, а также экипировать оружие и броню.

Максимальное здоровье равно базовому здоровью класса плюс 15 за каждый уровень после первого. У воина базовое здоровье 120, у следопыта 100, у мага 85. Бонус урона героя равен 3 за каждый уровень после первого. Порог опыта для следующего уровня равен текущему уровню, умноженному на 100.

gain_experience добавляет опыт и в цикле проверяет достижение порога. Порог вычитается до повышения уровня. Цикл позволяет получить несколько уровней за одну награду. Например, 350 опыта с первого уровня дают второй уровень за 100, третий за 200 и остаток 50; следующий порог составляет 300.

Метод equip принимает предмет из инвентаря. Новое оружие или броня удаляется из инвентаря, старый экипированный предмет возвращается туда. Экипированные предметы отдельно от инвентаря, поэтому обычная продажа их не предлагает.

Свойство inventory возвращает tuple. Пользователь кода не может добавить предмет через hero.inventory.append(...), но сами предметы внутри кортежа остаются изменяемыми. Подчёркивание в _health или _inventory обозначает внутреннее поле по соглашению, а не абсолютный запрет доступа.

## 12 Враги и алгоритм боя

Enemy расширяет Combatant контрактом награды: experience_reward и roll_gold_reward. AbstractEnemy реализует общие поля здоровья, диапазон урона, получение удара и награды. _reduce_damage — точка изменения сопротивления конкретного врага.

| Враг | Здоровье | Базовый урон | Опыт за победу | Золото за победу |
|---|---|---|---|---|
| Гоблин | 50 | от 6 до 14 | 40 | от 15 до 30 |
| Скелет | 110 | от 10 до 24 | 90 | от 35 до 70 |
| Дракон | 260 | от 16 до 22 | 500 | от 200 до 400 |

Скелет уменьшает входящий урон на 30 процентов. Дракон уменьшает входящий урон на 25 процентов и с вероятностью 25 процентов удваивает свой урон огненным дыханием. Это отражается как критический удар.

Battle.run увеличивает номер раунда и вызывает удар героя. Если враг выжил, вызывает его ответный удар. Цикл продолжается, пока оба живы. После завершения определяется исход и возвращается BattleReport.

Battle._strike получает Hit у атакующего, передаёт числовой урон в receive_hit защищающегося, записывает событие удара и при нулевом здоровье добавляет DEATH. Убитый враг ответного удара не наносит.

Урон по герою сначала уменьшается бронёй и округляется; затем применяется минимум 1. Урон по врагу проходит через его сопротивление и тот же минимум. Здоровье ограничивается снизу нулём.

Особенность исходного примера: receive_hit возвращает урон после защиты, который может превышать оставшееся здоровье. Если у врага 5 здоровья, а удар равен 18, в событии будет 18 урона и 0 здоровья. Это величина рассчитанного удара, а фактическое уменьшение здоровья составит 5. Данная семантика сохранена.

## 13 Фабричный метод Factory Method

Основной файл — world/location.py. Абстрактная локация содержит общий сценарий экспедиции, а создание конкретного врага передаёт подклассу.

```python
class Location(ABC):
    @abstractmethod
    def _create_enemy(self) -> Enemy: ...
```

Реализации в конкретных локациях:

```python
# Внутри Forest
def _create_enemy(self) -> Enemy:
    return Goblin()

# Внутри Crypt
def _create_enemy(self) -> Enemy:
    return Skeleton()
```

Третья реализация — DragonLair, возвращающая Dragon. Возвращаемый контракт во всех случаях — Enemy. Общий код explore вызывает self._create_enemy(), поэтому конкретный тип выбирается через переопределённый метод объекта локации.

Преимущество: новый вид экспедиции может создавать другого врага, сохраняя общий алгоритм. Недостаток: новые варианты часто требуют новых подклассов создателя. В этой игре локации также отличаются добычей и названием, поэтому отдельные классы имеют содержательный смысл.

Метод explore одновременно иллюстрирует Шаблонный метод: базовый класс задаёт последовательность шагов, некоторые из которых уточняют наследники. Шаблонный метод — поведенческий паттерн; он не заменяет обязательный Фабричный метод, а работает вместе с ним.

Называть любой метод с create Фабричным методом неправильно. Для данного паттерна существенна структура: общий алгоритм создателя вызывает переопределяемое создание продукта. ItemCatalog.create по устройству является поиском и копированием прототипа, а не основным примером Factory Method в этой работе.

## 14 Экспедиция награды и случайность

Location.explore получает героя и необязательный seed. Если seed не передан, Dice.next_seed выбирает его автоматически. Затем reseed устанавливает состояние общего генератора.

Последовательность экспедиции: установить seed; восстановить здоровье героя; создать врага; запустить Battle; начислить награду или штраф; вернуть ExpeditionReport.

При победе _reward вычисляет опыт, случайное золото и добычу. _roll_loot с вероятностью 0,6 создаёт предмет из таблицы локации. При наличии предмета с вероятностью 0,3 он получает подходящее зачарование. Затем опыт и золото передаются герою, а добыча — в его инвентарь.

В лесу возможны гоблинский тесак, охотничий лук и кожаная броня. В склепе — клинок рыцаря, костяной лук, посох некроманта и кольчуга стража склепа. В логове дракона — клинок рассвета и броня из драконьей чешуи.

При поражении _punish вычисляет hero.gold // 2, списывает эту сумму и возвращает награду с отрицательным gold. Отрицательное значение в Rewards обозначает изменение баланса, а не отрицательный остаток золота.

Один seed сам по себе не гарантирует одинаковый отчёт. Нужны одинаковое исходное состояние героя, одинаковая локация, код и последовательность вызовов генератора. Если герой вырос в уровне, сменил оружие или раньше убил врага, число бросков и результат могут измениться. Для сравнения лучше создавать двух одинаковых новых героев.

Не следует ожидать одинаковых чисел от Java и Python только потому, что им передали seed 7. В этой работе проверяется воспроизводимость повторного запуска одной Python реализации при одинаковых условиях.

LocationRegistry хранит локации по коду, возвращает выбранную через get и список через all. Неизвестный код вызывает UnknownCodeError, как и неизвестный предмет в каталоге.

## 15 Торговец и консоль

Merchant хранит каталог и набор кодов продаваемых предметов. showcase возвращает копии товаров для показа. buy проверяет наличие кода в ассортименте, создаёт копию предмета, списывает цену и добавляет покупку в инвентарь. При нехватке золота spend_gold вызывает ValueError до добавления покупки.

sell сначала удаляет предмет из инвентаря, затем начисляет половину его текущей цены с округлением вниз. Если предмета нет в инвентаре, продажа не выполняется. Цены учитывают зачарования.

ConsoleView.describe формирует описание предмета; print_hero показывает характеристики; print_report проходит по событиям боя и выводит результат экспедиции. main.py обрабатывает меню и выбор игрока. read_choice возвращает индекс от 0 до count − 1, а при некорректном вводе — −1.

Разделение позволяет заменить способ вывода, не меняя классы боя, предметов и локаций. При этом main по-прежнему остаётся консольным управляющим кодом; полноценный другой интерфейс потребует своего входного слоя.

## 16 Формулы и примеры расчётов

Значения выражены в игровых единицах: здоровье, урон, опыт и золото. Это правила программы, а не физические величины.

Максимальное здоровье: Hmax = Hbase + (L − 1) × 15. Для воина уровня 3: 120 + (3 − 1) × 15 = 150 единиц здоровья.

Урон героя: Dhero = Dweapon + (L − 1) × 3. С тренировочным мечом на уровне 3: 12 + 2 × 3 = 18 единиц урона.

Защита брони: A = min(Abase + сумма бонусов защиты, 0,75). Для кольчуги с WARDING: min(0,30 + 0,10; 0,75) = 0,40, то есть 40 процентов.

Урон по герою: Dreceived = max(1, round(Dincoming × (1 − A))). При входящем уроне 12 и кольчуге: max(1, round(12 × 0,70)) = max(1, 8) = 8 единиц урона.

Новое здоровье: Hafter = max(0, Hbefore − Dreceived). При 150 здоровья и уроне 8: max(0, 150 − 8) = 142 единицы здоровья.

Урон по скелету: max(1, round(Dhero × 0,70)). При Dhero = 18 получаем round(12,6) = 13 единиц урона.

Диапазон посоха: Dmin = round(D × (1 − s)); Dmax = round(D × (1 + s)). Для посоха с D = 14 и s = 0,30: round(9,8) = 10 и round(18,2) = 18 единиц урона.

Критический удар лука на уровне L: Dcrit = 2 × Dweapon + (L − 1) × 3. Для лука с уроном 10 на уровне 3: 2 × 10 + 2 × 3 = 26 единиц урона.

Порог опыта: XPnext = 100 × L. На третьем уровне нужно 300 единиц опыта до четвёртого. В поле experience хранится остаток относительно текущего порога, а не весь опыт за игру.

Цена продажи: Psell = Pitem × 50 // 100. Предмет стоимостью 91 золото продаётся за 91 × 50 // 100 = 45 золота.

Потеря при поражении: Glost = Gbefore // 2. При 51 золоте потеря составляет 25, остаток — 51 − 25 = 26 золота.

Для случайной победной экспедиции вероятность получить зачарованную добычу по заданным двум проверкам составляет 0,6 × 0,3 = 0,18, то есть 18 процентов. Это расчёт по игровым вероятностям, а не измеренная доля на малой серии запусков.

Python round округляет точные половинные значения к ближайшему чётному целому: round(8.5) = 8, round(9.5) = 10. Оператор // выполняет целочисленное деление с округлением вниз; в игровых денежных расчётах используются неотрицательные числа.

## 19 Материал для защиты

### 19 1 Что такое шаблоны проектирования и зачем они нужны

Шаблон проектирования — описание повторяющегося решения задачи проектирования. Он объясняет роли объектов и их взаимодействие. Это не готовая библиотека и не обязательный способ решения любой задачи. Польза — общая терминология, понятная структура зависимостей и возможность менять части программы с меньшим числом правок. Цена — дополнительные абстракции, которые могут быть избыточны в простой задаче.

Три основные группы: порождающие управляют созданием объектов; структурные — составом классов и объектов; поведенческие — алгоритмами и взаимодействием. В данной работе обязательны пять порождающих паттернов. Дополнительно в explore виден поведенческий Шаблонный метод.

### 19 2 Что такое порождающие паттерны и какие задачи они решают

Они отделяют решения о создании объектов от кода их использования. Такие решения включают выбор конкретного класса, согласование семейства продуктов, пошаговую сборку, копирование настроенного объекта и контроль общего экземпляра.

Примеры из работы: Battle использует Combatant и не создаёт конкретных врагов; Location передаёт создание врага подклассу; Builder получает комплект от StarterKitFactory; ItemCatalog выдаёт копии; Dice предоставляет общий генератор.

### 19 3 Одиночка назначение реализация плюсы минусы применение

Назначение — один общий экземпляр с точкой доступа. Реализация — поле класса Dice._instance и __new__, возвращающий сохранённый объект. Проверка — Dice() is Dice() даёт True.

Плюсы — единое состояние генератора и простой доступ. Минусы — глобальное состояние, скрытые зависимости, сложность изоляции тестов и отсутствие синхронизации ленивого создания. Применять, когда совместное использование одного объекта является осознанным требованием. Альтернатива для этой игры — явно передавать один генератор через зависимости.

### 19 4 Строитель назначение реализация плюсы минусы применение

Назначение — собрать сложный объект по шагам и проверить перед созданием. Реализация — Hero.Builder, методы set_name, set_hero_class, set_starter_kit, set_level, set_gold и завершающий build. Каждый set возвращает self. build проверяет обязательные поля и вызывает Hero(self).

Плюсы — читаемые шаги, значения по умолчанию и целостная проверка. Минусы — больше классов и кода, возможное недопустимое промежуточное состояние. Применять для сложной сборки и проверок. По сравнению с длинным позиционным конструктором меньше риск перепутать параметры; в Python именованные аргументы остаются полноценной более простой альтернативой для простых случаев. Отдельный Director в этой реализации не требуется.

### 19 5 Прототип назначение реализация плюсы минусы применение

Назначение — создавать объект копированием заранее настроенного образца. Реализация — Item.copy и ItemCatalog.create. Каталог хранит прототипы и не выдаёт их напрямую.

Плюсы — клиенту не нужно знать конкретные конструкторы и весь процесс настройки. Минусы — сложность корректного копирования вложенного состояния и графов ссылок. Применять, когда экземпляры удобно получать из подготовленных образцов. В игре так создаются покупки, добыча и стартовое снаряжение.

### 19 6 Глубокое и поверхностное клонирование

При поверхностном копировании появляется новый внешний объект, но вложенные ссылки первоначально общие. При глубоком копировании рекурсивно копируется вложенное состояние в соответствии с механизмом копирования.

В Item.copy после copy.copy отдельно создаётся list(self._enchantments), иначе одна копия могла бы менять общий список. Сами Enchantment можно разделять, потому что их поля неизменяемы. Если появится новый изменяемый список, словарь или другой объект состояния, его тоже нужно учесть. Глубокая копия не гарантирует, что копировать абсолютно любой ресурс будет допустимо и осмысленно.

### 19 7 Фабричный метод назначение реализация плюсы минусы применение

Назначение — позволить наследникам выбирать создаваемый продукт, сохранив общий алгоритм создателя. Реализация — Location._create_enemy, вызываемый из Location.explore. Forest возвращает Goblin, Crypt — Skeleton, DragonLair — Dragon.

Плюсы — независимость общего сценария от конкретного врага и расширение через наследование. Минус — рост числа подклассов. Применять, когда общий алгоритм должен создавать объект, тип которого зависит от специализации создателя. На защите нужно показать не только методы в наследниках, но и строку их вызова в explore.

### 19 8 Абстрактная фабрика назначение реализация плюсы минусы применение

Назначение — создавать семейства связанных продуктов через общий интерфейс. Реализация — StarterKitFactory с create_weapon и create_armor. Конкретные фабрики воина, следопыта и мага создают свои комплекты через каталог.

Плюсы — согласованность семейства и замена набора через объект фабрики. Минус — новый вид продукта требует изменить все фабрики. Применять, когда нужно выбирать целые комплекты и состав комплекта относительно стабилен. На защите показать два порождающих метода и минимум две реализации с разными результатами.

### 19 9 Чем Фабричный метод отличается от Абстрактной фабрики

| Критерий | Фабричный метод | Абстрактная фабрика |
|---|---|---|
| Основная задача | Изменять создаваемый продукт в специализациях создателя | Создавать согласованные семейства продуктов |
| Основной механизм | Переопределение метода в наследнике | Передача объекта с набором фабричных методов |
| Пример создателя | Location и его наследники | StarterKitFactory и фабрики классов героя |
| Продукты в работе | Enemy с конкретными типами врагов | Weapon и Armor для выбранного класса |
| Клиент в работе | Общий сценарий explore | Hero.Builder.set_starter_kit |

Число методов само по себе не является полным определением различия. Главное — задача паттерна и организация зависимостей. Абстрактная фабрика может внутри использовать фабричные методы или прототипы; в этой работе она обращается к каталогу прототипов.

### 19 10 Дополнительные вопросы по Python и архитектуре

Что такое self. Это ссылка на текущий экземпляр; через неё читают и изменяют его состояние. Что такое cls. Это класс, переданный в __new__ или classmethod. В Dice именно у cls хранится общий экземпляр.

Зачем from __future__ import annotations. Чтобы отложить вычисление аннотаций и удобно ссылаться на класс, который ещё определяется, например Dice или Hero.Builder. Аннотации описывают ожидаемые типы, но сами по себе не проверяют аргументы во время исполнения.

Зачем @property. Позволяет читать вычисляемое или контролируемое значение как атрибут: hero.max_health. Отсутствие сеттера запрещает обычное присваивание через это свойство, но не закрывает внутренние поля средствами безопасности.

Что даёт @dataclass. Автоматически создаёт стандартные методы, например __init__, __repr__ и __eq__, для класса данных. frozen=True ограничивает присваивание полям. Это не глубокая заморозка всех вложенных объектов.

Зачем TypeVar T и Sequence[T] в Dice.pick. Чтобы показать связь типа элементов входной последовательности и возвращаемого элемента. Если передана последовательность строк, ожидаемый результат — строка. Во время обычного выполнения это не отдельный механизм проверки типов.

Зачем UnknownCodeError наследуется от LookupError. Ошибка означает, что объект не найден по коду. Сообщение содержит вид объекта и неизвестный код. ValueError используется при недопустимых значениях, например отсутствии имени или нехватке золота.

Где наследование. Hero и Enemy реализуют Combatant; конкретные враги наследуются от AbstractEnemy; конкретные локации — от Location; фабрики наборов — от StarterKitFactory.

Где композиция. Герой хранит ссылки на оружие и броню, торговец — на каталог, локация — на каталог, Battle — на участников. Строитель получает объект фабрики набора. Эти объекты используются как составные части взаимодействия.

Где полиморфизм. Battle вызывает roll_damage и receive_hit через общий контракт, а поведение зависит от конкретного героя или врага. Location.explore вызывает _create_enemy, и реализация выбирается по классу локации.

Почему общий алгоритм не должен знать Goblin и Skeleton. Тогда добавление другого врага потребует меньше правок: общий бой работает с Combatant, а экспедиция — с Enemy. Конкретные классы нужны в местах их создания и регистрации.

Можно ли вызвать _create_enemy снаружи. Технически да: одно подчёркивание — соглашение. В обычном сценарии его вызывает explore. Тест может вызвать его напрямую для проверки типа созданного продукта.

Почему при одинаковом seed вывод отличается после повторной экспедиции. Герой мог получить уровень или сменить снаряжение, поэтому исходное состояние и число случайных вызовов изменились. Нужно сравнивать два одинаково настроенных новых героя.

Почему в состоянии героя показывается максимальное здоровье. ConsoleView.print_hero использует hero.max_health, как в примере; внутри отчёта удара выводится фактическое здоровье после удара. Перед новой экспедицией оно восстанавливается.

Что произойдёт при новом классе героя. Нужна новая фабрика набора и запись в HeroClass; если используются новые предметы — регистрация в каталоге. Боевой алгоритм менять не требуется. Что произойдёт при новом продукте стартового набора. Потребуется изменить контракт StarterKitFactory, все фабрики и потребителя продукта.

Есть ли ограничение экипировки по классу героя. Нет. Фабрика определяет только стартовый набор. Какие действия игрока не предусмотрены. Выбор удара внутри раунда, использование зелий и сохранение прогресса в файл не входят в исходный пример.

Почему классы и функции распределены по файлам. Это сохраняет структуру учебного пакета, делает зависимости видимыми и позволяет отдельно изменять бой, предметы, создание героя и интерфейс. Сама разбивка по файлам не является отдельным паттерном.

### 19 11 Готовый текст объяснения на защите

В этой лабораторной работе реализована текстовая RPG на Python. Герой выбирает класс, получает стартовое снаряжение, ходит в экспедиции, сражается и получает награды. Цель работы — показать пять порождающих шаблонов проектирования.

Одиночка реализована в Dice через __new__ и поле _instance. Повторные обычные вызовы Dice возвращают один объект. Это общий источник случайности, который можно переинициализировать заданным seed.

Прототип реализован в Item.copy. Каталог хранит шаблоны и возвращает их копии. При копировании отдельно создаётся список зачарований, чтобы изменение предмета не меняло шаблон.

Абстрактная фабрика — StarterKitFactory. Она создаёт два связанных продукта: оружие и броню. Фабрики воина, следопыта и мага дают разные стартовые комплекты. Строитель героя использует выбранную фабрику.

Строитель — вложенный Hero.Builder. Он принимает параметры по шагам, а build проверяет обязательные поля и создаёт героя. Методы возвращают self, поэтому их можно объединять в цепочку.

Фабричный метод — Location._create_enemy. Общий explore восстанавливает героя, получает врага через этот метод, запускает бой и начисляет награду. Лес создаёт гоблина, склеп — скелета, логово — дракона. Общий алгоритм от конкретного врага не зависит.

### 19 13 Краткая памятка

Singleton — один общий Dice. Builder — пошаговая сборка и проверка Hero. Prototype — копирование Item из каталога. Factory Method — выбор врага через наследников Location. Abstract Factory — согласованные Weapon и Armor через фабрику набора.

Главные строки для объяснения: __new__ возвращает сохранённый объект; set методы возвращают self; build валидирует; copy.copy создаёт оболочку, list отделяет изменяемый список; explore вызывает переопределённый _create_enemy; фабрика набора содержит два порождающих метода.
